# Local production and continuous delivery v1

## Scope
Local workstation production only: development on 127.0.0.1:3000, production on 127.0.0.1:3100, verification on 3200/3201. No LAN/public hosting, Windows service, remote push, automatic GitHub trigger or reboot autostart is installed. Restrict Windows account access to the production folder, especially shared/config. This is explicit tested-commit continuous delivery, not automatic deployment of dirty changes.

## First installation
Stop the current development batch-launcher window. Run from D:\monorepo\NewModularProduct:

    py .\tools\patches\local-production-v1\install.py --apply
    py .\tools\patches\local-production-v1\install.py --check
    py .\tools\deploy\local_delivery.py plan

The installer changes source/tooling only, not Git history, .env or live data. It runs 8 runtime-isolation tests and 18 controller tests with synthetic repositories/databases. The plan command creates a versioned template snapshot under tools/deploy/assets and pins the installed Google-worker dependency closure under tools/deploy/requirements.lock.txt. It creates a JSON plan and readable Markdown review under var/maintenance/delivery. Inspect the listed new/changed files and git diff locally. Do not use git add . . Existing staged work blocks the procedure. Pattern-based scanning is not a guarantee against all private content. Existing unusual tracked files are not silently deleted; private/generated/unrecognised root files are excluded from release extraction.

After reviewing the exact printed plan, run:

    py .\tools\deploy\local_delivery.py checkpoint --plan <printed-plan-json-path>
    py .\tools\deploy\local_delivery.py init --seed
    py .\tools\deploy\local_delivery.py deliver --ref HEAD

Use PowerShell exit-code checks between commands as shown in the accompanying answer. Do not continue after a failure.

Checkpoint tests a separate source snapshot with locked dependency installs, every discovered Node *.test.js file, Python worker tests, controller tests and Playwright browser tests. Only then does it explicitly stage the reviewed paths, remove listed generated bytecode from TRACKING ONLY (local files kept), commit and make an annotated baseline-localprod tag. It never pushes. Real Git hooks are not disabled; detected hook/concurrent scope changes prevent a tested tag and are reported without rewriting history. A failure after staging can leave reviewed paths staged; inspect them rather than reset unrelated work.

Initialisation requires the previously created bootstrap marker. --seed copies the known application/import/outreach databases through SQLite backup + quick_check and copies contacts JSON to production. Stop all other writers; the port check is a guard, not proof that arbitrary external tools stopped. Development originals stay intact. Seeding only works into empty production data and is NOT a later sync mechanism. Omit --seed for deliberately empty production stores. CV inventory is copied to shared/reference; actual CV PDF inputs remain at their configured external location and are not renamed or copied.

Initialisation reads development .env LOCALLY and imports selected provider/candidate configuration into a NEW shared/config/production.env outside Git. It does not print it or change the source .env. All integrations initially OFF. If initialisation fails after a partial copy, inspect it: the tool refuses to overwrite existing state automatically.

Deliver extracts only a committed Git tree. It installs separate dependencies in the release and repeats clean verification against that exact commit, checks health with synthetic state, asks a running production supervisor to pause gracefully, backs up coordinated state and tests candidate startup on a COPY of production state with integrations disabled. Existing schema changes and incompatible declared storage contracts block promotion. Active release metadata switches atomically. Existing data and mail history are never restored/rewound automatically.

## Launch

    D:\NewModularProduct-Production\start-production.bat

Keep that console open. It runs a production-owned supervisor copy, not a mutable development launcher. Production URL:

    http://127.0.0.1:3100/
    http://127.0.0.1:3100/healthz

Health must report production and the promoted commit. If no supervisor was running during deliver, this first launch is required; the promotion command does not claim the app is already running. The original start-local-server.bat remains the DEVELOPMENT launcher and now sets NMP_ENV=development.

Development defaults Gmail and paid integrations OFF, with live credentials cleared while disabled. NMP_ALLOW_DEVELOPMENT_INTEGRATIONS=true is an explicit opt-in for controlled integration testing; do not run development and production against the same real outreach.

After first production health/UI validation, deliberately enable the established flags in production.env and restart the production batch launcher. Credentials/permissions are not changed by deployment. Every Gmail message still needs its established content-specific confirmation. No health check creates a draft or sends mail.

## Subsequent delivery

    py .\tools\deploy\local_delivery.py plan
    # Review the new plan locally, then:
    py .\tools\deploy\local_delivery.py checkpoint --plan <new-plan-json>
    py .\tools\deploy\local_delivery.py deliver --ref HEAD

Developing does not change the running production release. Stop development for full verification because legacy tests may reference port 3000. Production remains available during tests; there is a brief controlled pause for backup/promotion, not zero downtime. With the supervisor running, deliver handles pause/switch/restart/commit-specific health verification. Logs and backups are under shared, outside code releases.

    py .\tools\deploy\local_delivery.py health
    py .\tools\deploy\local_delivery.py status
    py .\tools\deploy\local_delivery.py rollback

Rollback switches CODE to the recorded previous verified release only after contract/schema checks on copied state. It never rewinds Gmail operation history. Future schema changes need a separately reviewed migration and recovery design. A failed/uncertain graceful shutdown does not force-kill the process. Do not blindly delete locks, retry mail operations or restore a historical outreach database after real messages may have been sent.

Failed release directories are retained with candidate.json and a log reference for diagnosis. They are never overwritten automatically. Inspect them before any manual cleanup/retry. A supervisor lock left after a crash similarly requires inspection.

Memory: verification needs free memory (Windows commit charge). It stops before starting, before the tests and before the browser tests when less than 3 GB is free (`NMP_MIN_FREE_MEMORY_GB` changes the threshold), and a crash that looks like low memory says so. Node tests run two files at a time and the browser tests use one worker. If it stops, close browsers and other large apps or restart Windows, then ship again; production is unchanged.

## Release backups

Each delivery copies `shared\data` to `shared\backups\before-<commit>-<time>`, and nothing removes them automatically. The System check page shows their count and size. To clean up, run this preview from the project root (it changes nothing):

```powershell
python tools\deploy\release_backups.py --production-root D:\NewModularProduct-Production --keep 10
```

It lists every backup, newest first, and prints a confirmation code for the plan. To go ahead, run it again with the same `--keep`, plus `--move-to <folder outside production>` (or `--delete` to remove permanently), `--apply` and `--confirm <code>`. It always keeps at least the newest 3, and touches only `before-<commit>-<time>` folders.

## Dependencies, testing and limits
Node 24+ with SQLite support is required. npm ci uses package-lock.json. A separate Python venv is created in each release; worker dependencies are pinned from the currently installed working closure. Node executable checksum and Python version are verified at production launch. The Python base runtime still belongs to this machine: this is not an OS/container image. Runtime updates require re-verification. Browser/dependency downloads require registry access and the full gates can take several minutes. Failing tests block commits/promotion rather than being bypassed.

The default ignored letter template becomes a reviewed versioned asset. Verification materialises templates/standard-cover-letter.md from that asset for tests; production uses the asset directory. Existing development template settings/data are not replaced.

Offline package evidence: 8 Node tests and 18 Python tests pass; installer syntax/lifecycle/recovery checks pass. Synthetic supervisor IPC is exercised on POSIX. Windows Ctrl+Break handling, real dependency installs, the complete application/browser suite, initial state migration and production startup still require local acceptance. The assistant has not committed the user's repository, deployed a live release or accessed Gmail.
